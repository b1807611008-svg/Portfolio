01FOUNDATION

Token

颜色、字体、间距等基础规则。作为唯一事实来源，为所有上层视觉能力提供统一变量。

color.primary: #2F8EE8
space.md: 16px
radius.card: 12px
不描述具体组件
02PRIMITIVES

Visual

图标、蒙层、文字等最小视觉能力。引用 Token，将抽象变量转换成可组合的视觉单元。

visual: title-primary
font: {type.heading}
color: {color.text-1}
不承担业务结构
03COMPOSITION

Component

描述组件结构、变体、状态与交互，明确可以如何使用，以及在什么边界内使用。

variant: compact | default
state: loading | empty
behavior: tap → detail
不重复基础样式
04ORCHESTRATION

Page

调用并编排已有组件，描述页面结构、顺序和业务上下文，不重复解释组件内部规则。

page: channel-home
uses: Header, FeedCard
layout: vertical-flow
只描述组合关系
APRIVATE

Assets

存放组件私有图片与图标资源，资源跟随组件归档，避免一次性素材进入并污染全局资产库。

components/feed-card/
├─ design.md
└─ assets/cover.webp
谁使用，谁管理
CORE PRINCIPLE核心原则

每一层只描述自己该负责的内容。

前面的规则越准确，AI 在页面层需要理解和猜测的内容就越少。
规则准确度↑AI 猜测成本↓

50+ 核心文件类型
MD Source of Design

design.md

描述从 Relay 设计稿中抽取出来的设计事实，包括页面结构、模块层级、布局关系、设计 token、组件组成和视觉语义。

用来回答：设计稿里到底有什么？

spec.md

把设计信息转译成开发可执行的实现规范，明确尺寸、间距、颜色、字体、组件规则和页面还原要求。

用来回答：开发应该如何实现？

behaviors.md

记录组件或页面的交互行为，例如 hover、click、loading、empty、error、disabled 等状态下的响应方式。

用来回答：用户操作后会发生什么？

variants.md

沉淀组件或模块的不同形态与状态变体，帮助后续复用、扩展和对齐多场景下的视觉差异。

用来回答：这个组件有哪些版本？

ai-schema.yaml

提供给 AI 或自动化流程读取的结构化 schema，用字段化方式描述组件、token、模块和校验规则。

用来回答：机器如何稳定理解这份设计？

assets/

集中管理从设计稿导出的图片、图标、截图和其他静态资源，保证 HTML 预览与实现过程有可追溯的素材来源。

用来回答：图片和图标资源在哪里？

CHANGELOG.md

记录每轮生成、人工修正、验证反馈和结构调整，让设计文档的演进过程可以被复盘和追踪。

用来回答：这份文档经历了哪些变化？

Real Problems

能生成，不代表生成正确。

01

结构问题

页面漏组件，或只生成组件占位，没有调用真实组件。

02

规范问题

虽然调用了组件 Design.md，但尺寸、状态和间距与规范不一致。

03

资源问题

Icon 还原度不足，组件私有资源与全局资源调用混乱。

04

验证问题

生成后只检查静态页面，没有继续走查选中态、横滑、内容填充和交互逻辑。

Problem Loop

问题闭环：反复测试、反馈并参与优化。

我连续在多个视频组件上重复运行、验证和走查，将偶发现象整理为可以复现的问题，并与正职同学一起讨论原因、反馈解决方向，部分内容参与到后续能力优化中。

不是测试一次，而是在多个视频组件和业务状态中重复运行，确认问题是否可复现。

不是个人修补结果，而是把问题整理成可讨论、可迭代的反馈，推动 Skill 能力优化。

我的目标不只是把设计成果换成文档供人查阅。否则，它仍然只是另一种形式的设计说明，并没有充分发挥 AI 可读资产的价值。

01ANNOTATION SKILL

组件自动标注

在组件整理过程中，我发现间距标注存在大量重复劳动。不同标注对象的颜色、优先级和伸缩行为都需要设计师反复判断与设置。

我将这些判断规则沉淀为标注 Skill，让 AI 自动识别对象关系并完成一致的规范标注。

输入
待标注组件与图层结构
规则
标注颜色 · 对象优先级 · 伸缩规则
输出
自动生成的规范标注
减少重复操作统一标注判断提升整理效率
